# PStack portability audit

This is a maintainer inventory of BStack's pinned PStack source, not a claim that every workflow was exercised on every host. The review covered all 50 upstream `SKILL.md` files, 23 Potato Mode playbooks, two agents, and their scripts and references. The pre-audit selection named 46 upstream skills; the other four were already replaced or excluded. BStack's [capability contract](../shared/skills/bstack-router/references/capabilities.md) applies to imported instructions, but its general warning does not make a concrete Cursor command work elsewhere.

`Supported` below means the instructions do not require a particular agent host in the paths examined. `Conditional` means the skill can run only after the named capability is available and checked. `Quarantined` means do not route a consumer into that playbook until BStack has an adapter. `Removed` means the skill should stay in the pinned upstream snapshot but leave the consumer catalog. These are packaging decisions, not changes to upstream files.

[`watch-pr`](../upstream/pstack/skills/poteto-mode/scripts/watch-pr/watch-pr) starts with Bun, and [`bootstrap.ts`](../upstream/pstack/skills/poteto-mode/scripts/bootstrap.ts) runs `bun install --frozen-lockfile` on first use (lines 25–52). The packaged `multi-phase-plan` command for `check-plan.mjs` is rewritten to an installed path; the unsupported host lifecycle and generated plan requirements remain the reason for quarantine.

Before a conditional workflow runs, setup or the agent must explain the needed model roles, host tool, local runtime, and optional service in plain language, then check availability. Missing access is a reported limit, never a silent switch to another service or a claim that cross-model verification happened. The static source audit and capability overlay do not by themselves establish live portability; the sampled package and CLI results below have narrower claims.

## Setup and verification lifecycle

The [setup map](../shared/references/setup-requirements.md) now names first-use requirements in plain language. Local planning, tickets, and manual grilling need no tracker or model setup. Autonomous grilling needs two distinct runnable model roles; a saved role selection is not a successful two-model run. GitHub PR publication needs authenticated `gh`. Independent PR review needs its configured reviewer CLIs and models. None of those optional requirements blocks a basic install.

The [shared headless launcher](../shared/model_cli.py) stores private argv templates so wrapped commands such as `launch claude -- {args}` work without shell interpolation. Package `doctor` reports optional CLI availability; `--live --workflow` sends bounded prompts to the selected roles. The PR review runner repeats its live role checks with its actual structured-output flags before fetching code for a new review, and autonomous grilling's default preflight stops on a broken CLI role. `to-pr` uses the same configured Codex launcher for its visual attempt. Its text probe cannot certify the image tool or the quality of a generated image. Native-host grilling roles still require observed host-level evidence, and Arena/Interrogate remain host-mediated workflows rather than users of this Python launcher. AMP is not yet a packaged host or launcher adapter.

New installs enable engineering auto routing and set project verification to `ask`. Upgrades keep both saved choices. The [verification policy](../shared/references/verification-policy.md) defines `off`, `ask`, and `auto` for focused `verify-<app>` creation or updates during feature work; an explicit full maintainer sweep remains separate. The project instructions carry that policy pointer even with auto routing off. The package manifest owns model-invocable names, rather than a second hard-coded runtime or verifier list.

A narrow shell [PR guard](../shared/github/pr_guard.py) is bound for each selected host independently of auto routing. It redirects direct `gh pr create` and body-replacing `gh pr edit` to `to-pr`. It does not intercept every possible forge API, and a configured binding is not proof that a host trusted or executed it. The package and runtime tests cover binding, command forms, safe upgrades, and settings persistence. The historical v1 baseline can be adopted on a clean clone only when its managed block matches the exact published bytes; edited blocks still conflict.

## Evidence and limits

The source layer and package checks, 29 package tests, 62 runtime tests, nine transport tests, 39 shared-workflow tests, 69 local-workspace tests, 25 layer tests, 71 GitHub workflow tests, and offline consumer installation passed on this development branch. The workspace HTTP tests needed loopback socket access; the restricted first run could not bind `127.0.0.1`, and the rerun passed. A live installed-package routing probe passed fresh and resumed turns on Codex, Claude Code, and Cursor, with evidence in `.bstack/verification/20261022T015756Z-installation-e35282/report.json`. Cursor's first run exposed a verifier false negative for a full-file content blob; the verifier was corrected and the successful run repeated. Grok's earlier routing probe did not reach a model because its local credentials had expired. A later bounded headless model probe did pass on Grok; routing continuity remains unverified there.

The new model launcher passed a four-CLI wrapper fixture and live short prompts on this machine. A disposable release install passed `doctor --live --workflow review-pr` with Claude Opus 5.5 medium, Codex Astra medium, and Claude Opus 5.5 high. The installed review runner also passed its exact structured-output doctor with those roles. Claude reported exact model usage; Codex accepted the requested model and answered but did not expose an independent model ID in the probe. A second disposable install passed autonomous grilling preflight with Codex 6.1 Sol and Claude Opus 5.5. Cursor's first text probe failed because its disposable directory was not trusted; adding `--trust` for that isolated directory made the probe pass. A separate Codex text probe passed for `to-pr`. No actual image-generation attempt was included in these doctor checks.

These checks establish file integrity, installation, selected-model prompt execution, and sampled routing behavior. A disposable feature-work pilot in `.bstack/verification/feature-auto-pilot/` observed Codex create a `verify-notes` skill under the `auto` verification setting; it does not establish that other hosts will maintain verifiers consistently. Live PR guard denial, desktop behavior, full visual generation, and every conditional imported workflow still need targeted tests before claiming full parity. The repository-local `verify.py doctor` also reports stale source-checkout adapter bindings; the passing installation probe uses fresh disposable consumer projects and is the relevant install evidence here.
