# A short bstack walkthrough

Teach BStack as a set of useful entry points, not a required pipeline. It brings together pinned work from Lauren Tan's PStack and Matt Pocock's skills, then adds BStack's own connections, local workspace, PR workflows, project baseline, and optional memory. Give the person a short map before going deep: they can enter at planning, code understanding, implementation, or a PR. Load only the skills that fit their task.

The project baseline is there from the start. Its seven rules push agents to challenge weak assumptions, find root causes, weigh implementation trade-offs, write meaningful tests, and explain work plainly. `unslop` applies to prose. Manual engineering routing is the default: invoke a named skill or `poteto-mode`. `bstack-auto on` lets ordinary engineering prompts enter that router. Neither mode loads the whole collection into every prompt or gives an agent authority to make product decisions.

Use a couple of these journeys to make the connections concrete. Pick the ones that match the person's work; don't recite all three by default.

- **A bug in existing code.** Use PStack's `how` and `why` to understand behavior and rationale when needed. With auto routing on or `poteto-mode` invoked, its engineering workflow joins the baseline in steering the fix toward the cause and its blast radius. Relevant ADRs can explain why an apparent shortcut was rejected before the agent proposes it again. A clear bug needs no Wayfinder map or ticket first.
- **An idea becoming a feature.** Matt's `grill-me` and Wayfinder approach can expose open decisions; BStack keeps the map locally, alongside optional specs and tickets. `prototype` can test a direction before committing to it. When the choice is ready, `handoff` carries accepted scope, evidence, and relevant ADRs into a fresh implementation context, possibly with a different model. PStack's engineering workflows take over there. A consequential new architecture choice can become a short ADR, while routine design picks stay out of that catalog. The developer can skip any phase that adds no value.
- **A PR that needs to land.** BStack's `to-pr` explains a new PR and checks overlapping work; `review-pr` asks independent models to challenge it when those CLIs are available; `resolve-pr` evaluates feedback before making a fix or replying. Review and resolution can start from an existing PR without replaying the planning journey. The same scope and decisions carry into the review, so another agent is not guessing what the author meant.

Continuity matters whenever one agent, model, or tool passes work to another. A selected Codex, Claude Code, Cursor, or Grok host gets the same packaged skill names in that project. The local workspace, handoffs, and repository ADRs keep project facts outside a single chat. Optional shared personal memory can carry approved preferences across Codex, Claude Code, and Cursor; it is separate from those project records and is never enabled by ordinary installation. BStack adapts a workflow to the host capabilities actually available and reports a missing capability rather than claiming it worked elsewhere. A new session may be needed after installation or an upgrade to discover the skills.

Use [common routes](routes.md) for another starting point. Stop once the person can see a path for their own task, then go deeper where they ask. Don't imply an external tracker, model role, desktop skill catalog, or personal memory is already configured.
